# US-015 — Convert a note into one Typst document: pipeline, order, and result

**Status:** Done (the `AssetIndex` over the Obsidian vault and the export command come with US-007 and US-008)
**Introduced:** v0.1.0
**Implemented:** —
**Supersedes:** —

---

## Story

**As a** maintainer of the converter,
**I want** one pure function that turns a note, its settings, and a read-only
view of the vault into the complete Typst file, the list of assets to copy, and
the warnings,
**so that** the rules of US-001 to US-006, US-008 to US-011 fit together in a
fixed, tested order, and the plugin shell only reads, writes, and compiles.

---

## Acceptance criteria

- **AC-1 (function and result shape):** `convert(input)` in `core/convert`
  takes
  ```
  source: string        the Markdown text of the note
  noteName: string      file name without extension ("Rules")
  notePath: string      vault path of the note ("Sample/Rules.md")
  settings: ConvertSettings   effective values after the precedence of US-008 AC-1
  assets: AssetIndex    read-only vault lookup, injected (AC-13)
  fonts?: FontInfo      hasGlyph(family, codePoint), injected (US-005 AC-6, US-010)
  ```
  and returns a promise of `{typ, assets, warnings, lineMap}`: the Typst source
  as a string, the assets to copy (AC-6), the warnings (AC-7), and the line map
  (AC-8). It reads and writes nothing itself: all access to the vault goes
  through the injected `AssetIndex` and `FontInfo`. The function is asynchronous
  because Obsidian's file API is (confirmed by the user 2026-10-16).

- **AC-2 (document skeleton and fixed order):** The `.typ` consists of these
  parts, in this order; a part that does not apply is left out, and every rule
  appears exactly once:
  ```
  1. header comment        // Generated by Obsidian2Typst from "Rules.md". Regenerated on every export.
  2. template import       #import "template.typ": *                          (US-008 AC-9, if a template is set)
  3. page                  #set page(...)                                     (US-009, emitPageSetup)
  4. text and fonts        #set text(...), #show ...: set text(...)           (US-010, when implemented)
  5. highlight colour      #set highlight(fill: rgb("#ffeb3b"))               (US-001 AC-13)
  6. heading numbering     #set heading(numbering: "1.1")                     (US-002 AC-1b)
  7. footnote restart      #show heading.where(level: 1): it => { counter(footnote).update(0); it }   (US-005 AC-4b)
  8. image helper          FIT_IMAGE_HELPER, 6 lines                          (US-003 AC-2b, only if an image was placed)
  8b. callout styles      callout-styles and the callout helper             (US-016 AC-11, only if the body holds a callout)
  9. cover                 the cover page                                     (US-011, when implemented)
  10. body                 the converted note
  ```
  One blank line separates the preamble (2 to 8) from the cover or body. The
  rules are registered by their owning stories in `core/convert/preamble.ts`
  with an id, an order number, and the text (ids and order numbers
  `template-import` 20, `page` 30, `text-and-fonts` 40, `highlight` 50,
  `heading-numbering` 60, `footnote-restart` 70, `fit-image` 80, `callouts` 85
  (US-016), `glossary` 86 (US-017), `cover` 90); a
  test fails if two rules share an id or an order number, or if a rule is
  emitted twice. The image helper rule (decided by the user 2026-10-17) is
  written only if the body contains at least one call of `fit-image` (a found
  image); a missing, remote or invalid image is a placeholder and does not need
  it. US-010 and US-011 register their rules when they are implemented; until
  then `convert` emits none of rules 4 and 9. The header comment contains no
  date, no version, and no absolute path (AC-9). With `headingNumbering: none`
  rule 6 reads `#set heading(numbering: none)`; rule 7 stays.

- **AC-3 (settings and built-in defaults):** `ConvertSettings` has the fields
  `page` (resolved geometry of US-009, **required**), `highlightColor`,
  `headingNumbering`, `externalLinkFootnotes`, `template` (boolean: a template
  is copied to the export folder), `cover` (US-011; a `convert` without it makes
  no cover, as mode `none`; the presets of US-008 always supply it) and later
  `fonts`. A missing
  optional field takes the built-in default:
  ```
  highlightColor         "#ffeb3b"
  headingNumbering       "1.1"
  externalLinkFootnotes  true
  template               false
  ```
  `convert` does not validate settings (US-008 and US-009 do); a value that
  breaks the contract (for example a colour that is not `#` plus 6 hex digits)
  throws a `TypeError`, because it is a programming error and not a problem of
  the note.

- **AC-4 (block spacing and file end):** Top-level blocks of the body are
  separated by exactly one blank line. The file uses LF only, even when the
  source uses CRLF, has no trailing spaces on any line, and ends with exactly
  one newline. The rule for trailing spaces covers the generated text; the
  lines of a code block are raw and keep their trailing spaces exactly (US-001
  AC-6). A source without any content (empty, frontmatter only, only
  comments) yields the header, the preamble, and the final newline, and
  compiles.

- **AC-5 (composed example, exact output):** With `notePath` =
  `Sample/Rules.md`, the settings `A5 print` of US-009 AC-6 and the other
  defaults of AC-3, this note
  ```
   1  # Rules
   2
   3  Intro with **bold**, a [link](https://example.org) and a [[Tessera]] reference[^1].
   4
   5  ## Tessera
   6
   7  - Strike
   8  - Parry
   9
  10  ![Map](assets/map.png)
  11
  12  | Weapon | Cost |
  13  |:--|--:|
  14  | Sword | 10 |
  15
  16  [^1]: See the table.
  ```
  (with `Sample/assets/map.png` present in the vault) gives exactly this
  `typ`:
  ```
   1  // Generated by Obsidian2Typst from "Rules.md". Regenerated on every export.
   2  #set page(width: 154mm, height: 216mm, margin: (top: 21mm, bottom: 25mm, inside: 23mm, outside: 18mm))
   3  #set highlight(fill: rgb("#ffeb3b"))
   4  #set heading(numbering: "1.1")
   5  #show heading.where(level: 1): it => { counter(footnote).update(0); it }
   6  #let fit-image(path) = layout(size => {
   7    let m = measure(image(path))
   8    let w = calc.min(m.width, size.width)
   9    let h = m.height * (w / m.width)
  10    image(path, width: w * calc.min(1, size.height / h))
  11  })
  12
  13  = Rules <h-rules>
  14
  15  Intro with *bold*, a #link("https://example.org")[link]#footnote[#link("https://example.org")] and a #link(<h-tessera>)[Tessera] reference#footnote[See the table.];.
  16
  17  == Tessera <h-tessera>
  18
  19  - Strike
  20  - Parry
  21
  22  #figure(fit-image("assets/map.png"), caption: [Map], numbering: none)
  23
  24  #table(
  25    columns: 2,
  26    align: (left, right),
  27    table.header([Weapon], [Cost]),
  28    [Sword], [10],
  29  )
  ```
  with `assets` = `[{from: "Sample/assets/map.png", to: "assets/map.png"}]`,
  `warnings` = `[]`, and the line map of AC-8. The two footnotes share one
  numbering (US-004 AC-1); the definition `[^1]:` leaves no text of its own.
  The `;` after the second footnote is the call separator of US-013: without it
  Typst would read the full stop as the start of a field access. A note without
  an image has the same text without lines 6 to 11 (the image helper rule is
  left out, AC-2).

- **AC-6 (asset plan):** `assets` lists each used asset once, in the order of
  first use, as `{from, to}` (the `AssetUse` of US-003 AC-4) with `from` as a
  vault path and `to` relative to the export folder, as defined by US-003 AC-4
  and US-011 AC-9. Nothing is copied by `convert`. An image used three times
  appears once. A missing or unsupported asset is not in the list (its
  placeholder and warning come from US-003 AC-5).

- **AC-7 (warnings and the registry):** `warnings` is a list of
  `{code, message, line}`, ordered by `line`, then by order of detection
  (US-006 AC-1); `line` is a line of the source file. `convert` never throws
  for any source text (AC-11); problems of the note become warnings. Every code
  that `src/core` can produce is listed in `docs/technical/warning-codes.md`
  with its owning story, message pattern, and a status: `active` (the code is
  produced by `src/core`) or `reserved` (its story is not implemented yet). A
  test compares the file with the code: every code used in `src/core` is
  listed, every `active` code is used, and a `reserved` code is not yet used,
  so that the owning story must flip it to `active` (decided by the user
  2026-10-17). The shell, not `convert`, applies strict mode (US-006 AC-4): if
  strict mode is on and `warnings` is not empty, it writes nothing.

- **AC-8 (line map):** `lineMap` is a list of `{typLine, sourceLine}` with one
  entry for every emitted `paragraph`, `heading`, `item`, `code`,
  `blockquote`, `thematic-break`, `table`, and table `row`, in output order;
  both lines are 1-based. For AC-5:
  ```
  typLine 13 -> sourceLine 1    (heading Rules)
  typLine 15 -> sourceLine 3    (paragraph)
  typLine 17 -> sourceLine 5    (heading Tessera)
  typLine 19 -> sourceLine 7    (item Strike)
  typLine 20 -> sourceLine 8    (item Parry)
  typLine 22 -> sourceLine 10   (paragraph with the image)
  typLine 24 -> sourceLine 12   (table)
  typLine 27 -> sourceLine 12   (header row)
  typLine 28 -> sourceLine 14   (row Sword)
  ```
  (without the image helper, every `typLine` is 6 less). The map is the base for
  the backlog story "Error mapping". An entry points at the first line of the
  emitted block. There is at most one entry per `typLine`: a block that is
  written on the line of its parent (the first block of an item) has the entry
  of the innermost block, not of the item. A footnote definition and an inline
  footnote have no entry: their text is written inside the paragraph that
  refers to them.

- **AC-9 (determinism and purity):** Converting the same input twice gives equal
  results, including the order of `assets` and `warnings`. A source with CRLF
  gives the same `typ`, `assets`, and `warnings` as the same source with LF.
  The output does not depend on time, locale, environment, or the order in
  which the injected lookups answer (a test lets `readHead` answer in reverse
  and in random order). `core/convert` imports only from `src/core` and
  `markdown-it` packages (enforced by lint and by the import test of US-014
  AC-5).

- **AC-10 (end to end against the compiler):** The `typ` of AC-5, with a
  template present, and the `typ` of the sample note `Book.md` (US-024; with fixture
  images supplied by a fake `AssetIndex`) compile with the bundled compiler in
  Node with zero errors, and the compiled text of AC-5 reads back as the
  intended content (heading `1 Rules`, `1.1 Tessera`, two footnotes `1` and `2`).
  No generated file uses an `@preview` package.

- **AC-11 (never throws, edge inputs):** `convert` returns a result, compiles,
  and does not hang for: an empty source, only frontmatter, only an HTML
  comment, a single line of 200000 characters, unclosed `**`, `^[`, `[[`, and
  `<!--`, control characters, and the malformed list of US-014 AC-4.

- **AC-12 (no silent loss of a node):** Every node kind of the tree of US-014
  AC-1b has an emitter, enforced by a type-level exhaustive check and a test
  over the list of kinds. A node that nevertheless reaches the emitter without a
  rule (for example a future kind) emits its text content and one warning
  `NODE_UNSUPPORTED` with the kind and the source line; it is never dropped
  silently (SCAR-009).

- **AC-13 (the vault lookup `AssetIndex`; decided by the user 2026-10-17):**
  ```
  interface AssetIndex {
    files: readonly string[];                       vault paths of all files
    readHead(path: string): Promise<Uint8Array>;    the first 16 bytes
  }
  ```
  `convert` first walks the tree once and collects every image reference
  (`![](...)` and `![[...]]`, also inside lists, quotes, tables, links, headings
  and footnote definitions). It then reads the head of every file whose file
  name (the last path segment, compared after NFC) equals the file name of a
  reference, once per file, and passes the paths and heads to the resolver of
  US-003 unchanged. A file of another name is never read, so a note without
  images reads nothing. A file whose `readHead` rejects is given to the resolver
  with an empty head, which gives `ASSET_INVALID` for it; `convert` does not
  throw. `AssetIndex` has no other access to the vault.

## Notes

- Boundary (CLAUDE.md): `src/core/convert` is pure; `src/plugin` reads the
  note, resolves the preset (US-008), builds `AssetIndex` and `FontInfo`, calls
  `convert`, applies strict mode, writes the files of US-007 AC-1, copies the
  assets of AC-6, and runs the compiler.
- Confirmed by the user 2026-10-16 (with the line-map entry kinds of AC-8): an
  asynchronous `convert`. Refined by the user 2026-10-17 (AC-13): the port is a
  file list plus `readHead`, and a first pass over the tree finds the files to
  read. The US-003 resolver stays synchronous; the other designs (the shell
  reads the heads of all vault images; asynchronous emitters) were rejected as
  slower for large vaults or as too large a change to tested code.
- AC-2 reserves the places of fonts (US-010) and cover (US-011); both stay out
  of the output until their stories are implemented, and they register their
  rules in `preamble.ts` with the order numbers above, so nothing else moves
  later.
- Changes to the first version of this story (2026-10-17): the composed example
  had `image(...)` and no helper, but the finished image emitter writes
  `fit-image(...)` and needs the helper (AC-2 rule 8, AC-5); the example had
  `...reference#footnote[See the table.].` without the call separator that
  US-013 requires; the asset plan used `{source, target}` and now uses the
  existing `{from, to}` of US-003.
- US-001 AC-11 (validity gate) and AC-12 (determinism) stay as their own
  criteria; this story proves them for the whole pipeline (AC-9, AC-10).
- The composed example is also the first fixture of the converter test suite
  (SCAR-002, SCAR-007); every later story adds its constructs to it only
  through new fixtures, never by changing these lines.
