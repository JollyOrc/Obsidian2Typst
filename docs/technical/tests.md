## Automated quality gate

Run the following before declaring any task complete or cutting a release.
All steps must pass; a failing step blocks the release.

```bash
npm run typecheck          # tsc --noEmit (strict)               -- exists
npm test                   # unit + plugin + tooling tests      -- exists
npm run test:integration   # compile and PDF checks              -- exists
npm run build              # tsc --noEmit, then esbuild -> main.js -- exists
npm run lint               # eslint + prettier --check           -- exists
npm run test:ac-coverage   # every AC has a test, no todo left   -- planned (ticket)
```

The release build script must run all of them automatically so a red suite
blocks packaging. See SCAR-006. Only `test:ac-coverage` is still planned;
until it exists the release checklist must say so explicitly.

### AC-coverage check (planned)

`npm run test:ac-coverage` must fail when
1. an acceptance criterion in `docs/user-stories/US-*.md` of a story with status
   `Ready`, `In Progress`, or `Done` has no test whose title starts with
   `US-NNN AC-x`; or
2. at release time, any `it.todo` is left in `tests/` (a todo may only be
   replaced by a real test, or by `it.skip` with a linked ticket).

## Test layers

| Layer | Folder | Runs with | Needs |
|-------|--------|-----------|-------|
| unit | `tests/unit/` | `npm test` | pure core only; no Obsidian, no file system, no compiler |
| plugin | `tests/plugin/` | `npm test` | fakes for the vault, notices, timers, events (no real Obsidian) |
| integration | `tests/integration/` | `npm run test:integration` | the bundled compiler and fixtures; PDF text and geometry checks; most wait for the spike (TICKET-001) |

Test titles start with the story and AC id (`US-004 AC-2: ...`) so the
coverage check and the map below can be derived from them. One stub exists per
distinct example in an acceptance criterion; replace each `it.todo` with a real
test before writing the implementation (SCAR-003).

Fixtures: `tests/fixtures/` holds small hand-made inputs and the generated
sample vault `tests/fixtures/sample/` (US-024; `npm run fixtures`), the large
fixture. No test reads the author's private vault.

---

## Test coverage expectations

- Every AC in every user story must have at least one failing test written
  **before** the implementation begins. See SCAR-003.
- Tests for features that touch more than one module must include at least
  one integration test spanning the interaction.
- A test may only be skipped with an explicit `skip` marker and a linked
  ticket. Silently-red tests are treated as bugs.

## Manual smoke tests

These cover what only a real Obsidian can show. The automated plugin tests use
fakes and do not replace them.

Procedures that need more than a few steps are manual checks, one file per check in [manual-checks/](manual-checks/) (`M01.md` to `M18.md`), listed with what each covers in the index [manual-checks.md](manual-checks.md) (split 2026-10-29, SCAR-029).

### §1 — Clickable warning line (US-006 AC-2b)

1. Export a note whose source has an unresolved link on a known line.
2. Open the generated vault note `<source name> export warnings.md`.
3. Click the line number in the table.
4. Expected: the source note opens with the cursor on that line.

### §2 — Preset management in the settings tab (US-008 AC-5, AC-6)

1. In a vault without the presets folder, enable the plugin.
2. Expected: the folder contains `A5 print.md` and `A4 digital.md`.
3. Create a preset, duplicate one, rename one, delete one in the settings tab.
4. Expected: notes appear, are renamed (links to them update), and the deleted
   note is in the trash; the last preset cannot be deleted.

### §3 — Editing a preset note by hand (US-008 AC-3, AC-4)

1. Open the side panel, then edit `A5 print.md` (change `bleed: 3` to `5`).
2. Expected: within 2 seconds the panel shows the new page size.
3. Break the YAML.
4. Expected: the preset is marked invalid with the error line, one notice
   appears, and the other preset still works.
